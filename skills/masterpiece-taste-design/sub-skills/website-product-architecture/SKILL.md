# Sub-Skill: Архитектура веб-страниц и экранов продукта

Руководство по проектированию логической структуры, компоновки и информационного ритма интерфейсов без шаблонных ограничений.

---

## 1. Карта целей секций вместо фиксированных схем

Вместо механического насаждения жесткой последовательности секций структура страницы определяется реальной задачей:

`
[ЭКРАН / СТРАНИЦА]
  │
  ├── 1. Навигация / Входной контекст (логотип, навигация, ключевой статус при необходимости)
  ├── 2. Первичный фокус (суть предложения, основной инструмент или рабочий экран)
  ├── 3. Смысловой блок данных (таблица параметров, каталог, перечень работ или возможности)
  ├── 4. Подтверждение надежности (настоящие факты, спецификации, документы, без фейковых отзывов)
  └── 5. Целевое действие и подвал (форма записи, кнопка перехода, контакты, реквизиты)
`

**Принцип гибкости:**
- Количество секций зависит от типа продукта: от 1-2 экранов (для утилиты или расписания) до 4-6 блоков (для витрины услуг или сложного продукта).
- Каждая секция обязана иметь явное назначение: если блок не помогает пользователю принять решение или выполнить операцию — он удаляется.
- Референс по планированию: см. [../../references/design-direction.md](../../references/design-direction.md).

## 2. Вариативность компоновки

Формат представления информации выбирается под структуру данных:

### 2.1 Таблицы и списки данных
- Незаменимы для расписаний, каталогов, реестров, финансовых выписок и технических характеристик.
- Плотная и наглядная подача данных эффективнее, чем попытка разбить 20 параметров на раздутые карточки.

### 2.2 Сетки из 3 колонок
- Допустимы и логичны, когда пользователю предлагается выбор из трех равнозначных тарифов, категорий или шагов процесса.

### 2.3 Асимметричные сетки (Bento)
- Уместны, когда один элемент существенно важнее остальных (например, интерактивный график занимает 2/3 ширины, а вспомогательные параметры — 1/3).
- Не навязывать пропорцию 7:5 как единственный допустимый вариант; пропорции задаются иерархией контента (1:1, 2:1, 3:1).

### 2.4 Центрированная и асимметричная композиция
- Центрированный заголовок и лаконичный hero уместны для минималистичных сервисов, поисковых строк или страниц подтверждения.
- Двухколоночный сплит (заголовок слева, форма или превью справа) уместен для конверсионных страниц и сложных инструментов.

## 3. Инженерные правила секций

### 3.1 Шапка и навигация
- Высота на десктопе: 56–72px, без перегрузки вертикального пространства.
- Пункты навигации не должны переноситься на вторую строку на стандартных разрешениях.
- Никаких декоративных пульсирующих индикаторов статуса, если нет реальной телеметрии.

### 3.2 Главный экран (Hero)
- Высота: подход content-first (высота определяется естественным потоком содержимого без принудительной фиксации). Если экран требует полноэкранной посадки: min-h-[100svh] для стабильной высоты без скачков при сворачивании мобильных панелей либо min-h-[100dvh] при динамической адаптации под видимую область.
- Заголовок: емкий, конкретный, без маркетинговой воды («инновационная революция»).
- Кнопка действия (CTA): лаконичный текст в одну строку (1–3 слова).
- Отсутствие обязательного «layer bleed» (-mt-12): наложения элементов допустимы только там, где они поддерживают пространственную логику, а не ради галочки.

### 3.3 Типографическая дисциплина и флюидное масштабирование
- Допустимо использование одной качественной гарнитуры (например, системного шрифта или Inter/Geist) для всего интерфейса с вариацией по начертаниям и размерам.
- При необходимости выразительного акцента допустима шрифтовая пара (например, дисплейный гротеск для заголовков и нейтральный гротеск для текста), но это не является обязательной догмой.
- **Флюидные заголовки через `clamp()`:** для предотвращения разрыва строк на смартфонах и планшетах крупный кегль задается формулой `font-size: clamp(2.5rem, 7vw, 5.5rem)` с отрицательным трекингом `tracking-tight` (-0.03em).

### 3.4 Двухфазная архитектура экрана (Scrollytelling & Interactive Stage)
- Для презентационных страниц эффективна двухфазная компоновка:
  1. **Hero Phase (100svh):** лаконичная фокусировка на сути инструмента, ключевое действие и главный визуальный объект.
  2. **Interactive Stage / Gallery Phase:** переход к детализации параметров, интерактивному калькулятору или структурированной витрине без раздувания искусственных секций.
- Справочник по кинетике и оптике: [../../references/motion_design_and_interactions.md](../../references/motion_design_and_interactions.md).

### 3.5 Живая консоль действия с физическим наложением (Overlapping Action Console)
- Канонический паттерн Архива 1 («Ветер»): главный блок интерактивного действия (поиск билетов, бронирование слота, калькулятор тарифа) размещается сразу под визуальной фото-панорамой первого экрана с отрицательным верхним отступом (`margin-top: -40px` ... `-50px`).
- Это создает осязаемую физическую глубину без искусственных размытых теней.
- Консоль включает переключение сервисов («Купить билет», «Регистрация», «Бронирование», «Статус»), форму с парными полями («Откуда / Куда» с кнопкой swap), дату и интерактивный поповер выбора параметров.
- Под консолью размещается лаконичная строка доверия (`trust-row`): 3 предметных преимущества без скрытых условий + лаконичный слоган.

### 3.6 Интерактивные микросценарии против дашбордизации (Anti-Dashboardization)
- **Запрещено** дробить посадочную страницу на 5 изолированных экранов через переключатели вкладок в React-стейтах (`currentTab === 'board' ? <Board /> : ...`). Посадочная страница должна оставаться единым скроллируемым пространством.
- Вторичные сценарии (выбор конкретного рейса из результатов поиска, карточка бронирования, детали багажа, интерактивный FAQ, форма входа) открываются в контекстных, быстрых модальных окнах с Focus Trap.

## 4. Запрет синтетических приемов

1. **Никаких выдуманных отзывов и клиентов:** не генерировать цитаты несуществующих вице-президентов и серые логотипы «Acme Corp».
2. **Никаких фальшивых телеметрических плашек:** метрики вида LATENCY 0.12ms или 99.998% UPTIME допустимы только в реальных DevOps-панелях. Пульсирующие зеленые точки на обычных сервисах запрещены.
3. **Честный копирайтинг:** язык должен описывать реальные функции и физические свойства, а не абстрактные лозунги.
4. **Канонический эталон реализации:** подробный архитектурный разбор см. в [../../references/archive_1_masterpiece_exemplar.md](../../references/archive_1_masterpiece_exemplar.md).
